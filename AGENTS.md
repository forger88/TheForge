# Agents working on TheForge

This file is for agent harnesses other than Claude Code working on TheForge itself (the template repository).
`CLAUDE.md` is the full source of truth; this file repeats only its load-bearing points so nothing is lost if a harness reads `AGENTS.md` alone.

## This project's own rules

- **Agent commit identity (Never).** Every commit an agent makes is authored and committed under the harness's own non-personal bot identity, never a personal address. A squash merge is authored by the hosting platform under the merging account's own no-reply alias and committed by the platform's own no-reply identity; that is acceptable. A real personal address is never acceptable in a commit author, committer, or `Co-authored-by:` trailer, head commit or squash alike. `scripts/check-merge-text.sh` (via `scripts/check-commit-identities.sh`) checks every head commit's identities and trailers against this before a merge, and its `--verify-merged` mode checks the squash commit's own identities after it; fix a violation forward with a new commit, never by rewriting history already on the default branch.
- **TheForge stays project-neutral (Never).** Never write a source or consuming project's product names, host-system names, repository paths, issue or PR numbers, domain vocabulary, module or class names, or configuration keys anywhere in this repository. Never reuse a real incident as a worked example, even renamed; invent a fresh generic one. Never name a person other than the upstream credits in the `THIRD_PARTY.md` files, the licence files, `template/NOTICE.md`, or a credited skill's own attribution file or frontmatter source-note; the human directing agents is "the owner" or "the user". Before pushing any change: run `pre-commit run --all-files` (this defaults to scanning against this repository's own committed `.theforge-denylist`, with `.copier-answers.yml`, `.forge/` and `.agents/skills/` excluded from the `no-issue-refs`/`denylist` hooks since they are rendered from `template/`, which stays scanned — `docs/forge-overrides.md`); for a back-port from a consuming project, point `THEFORGE_DENYLIST_FILE` at a session-local denylist naming that project's own terms instead, kept outside every repository — this unions with the committed default for that run, so the owner's own terms stay checked too; then have a fresh, context-free reviewing agent read the diff and raise every oddly specific term or example as a finding. Before merging: run `scripts/check-merge-text.sh <pr-number>` and merge with exactly the message it checked (or, for a hand-written or platform-default message, write it to a file and re-run with `--message-file <file>` first), then run `scripts/check-merge-text.sh <pr-number> --verify-merged` (same `--message-file`, plus the `--head-sha` the scan printed) to confirm the landed squash commit carries exactly that message — the pre-commit hooks above never see a PR's title, body, or the message actually written at merge time. The script tries the REST API directly with a bearer token before falling back to `gh api`; when neither can produce a scan, fix the blocker or escalate it, and do not merge on a manual approximation instead.
- **Where things live.** `template/` is everything a generated project receives; `copier.yml` at the root configures it. `template/.forge/` holds the forge-owned rule files: one topic per file, one sentence per line. `template/.agents/skills/` holds the skills; adapted upstream skills keep their source note and their row in `template/.agents/skills/THIRD_PARTY.md`. Project-owned seed files are listed under `_skip_if_exists` in `copier.yml`. `docs/adr/` holds TheForge's own decisions: Copier for distribution (ADR-0001), forge-owned versus project-owned separation (ADR-0002), the neutrality guards (ADR-0003), the raw-clone pre-commit tripwire (ADR-0004), the private staging repository's own committed denylist (ADR-0005), the single `CLAUDE.md` forge entrypoint and its migration (ADR-0006), retrofitting an existing project with a real `copier copy` (ADR-0008), TheForge consuming its own template (ADR-0009), and the Main Health TheForge thread owning this repository's own cadences (ADR-0010). A clone with no remote naming `forger88/TheForge` or `forger88/TheForgeStaging` fails `scripts/check-not-raw-clone.sh` on commit (ADR-0004); add an `upstream` remote pointing at it if you're working from a fork.
- **This repository's own post-merge review.** `.forge/post-merge-review.md` and the rendered `.agents/skills/post-merge-review/SKILL.md` now carry the tracker's body shape, batching, worktree-per-subsystem procedure, MoSCoW triage and pending-note convention, the same as for a generated project. Project-owned on top of that: render-check with `copier copy --trust --defaults --skip-tasks --vcs-ref HEAD .` wherever a finding needs checking against rendered output; the neutrality axis named in every brief, graded a Must on a miss; an extra cadence trigger before each snapshot into the public TheForge repository (cadence owner: the Main Health TheForge thread, ADR-0010); the interim health routine until this repository consumes its own template (ADR-0009): each firing, Main Health TheForge runs `pre-commit run --all-files` on `main`'s head (includes `check-render`) and reports red the way a consumer reports red CI, and posts any missing pending note, as a comment on the tracker, never an edit to its body. This repository still has no requirements specification of its own (checks diffs against `CLAUDE.md`/`AGENTS.md`/the ADRs instead, until the stage-0 follow-up); the architecture-findings epic (`arch_findings_epic` in `.copier-answers.yml`) now exists, so the earlier "no architecture-findings epic" exception no longer applies — see `CLAUDE.md`'s fuller section.
- **Tagging a release of this repository.** Unlike a generated project (owner-only tagging, `.forge/process-and-evidence.md`), an agent is allowed to tag and push a release of this repository itself — a recorded owner waiver of that imported rule, since the owner won't create releases here by hand and Copier otherwise syncs every consumer to `HEAD` with no reviewed-and-good point ever declared. Tag only after a post-merge review run covers its whole window with no open Must findings and `scripts/check-render.sh` passes on the commit being tagged; the tag goes on that review's watermark commit; before tagging, ask the owner whether to run a fresh, unpublished `scripts/local-full-suite.sh` pass against that commit first, and the owner decides. `vMAJOR.MINOR.PATCH` (PEP 440 order), MINOR for a change consumers must act on, PATCH otherwise, staying on `0.x` until the owner says otherwise; the release's notes are drafted with the `release-notes` skill (SDLC-112 then makes using it mandatory) into a section of the committed `docs/release-notes.md`, and the tag message is a copy of that section; `docs/release-notes.md` gets a warn-only exemption from the `no-issue-refs` hook for this reason, but the denylist scan still runs on it normally. There is no standing approval to push a tag: before pushing, ask the owner by name for explicit authorization naming the exact tag and version, and record their quoted reply on the ticket or thread where the release was requested — every tag push, not just once up front. Only then `git tag -a` and `git push` the tag, then record it on the post-merge review run's archive comment. A real constraint: `git push <tag>` can be denied outright by the harness's own permission classifier, with no GitHub-tooling fallback for creating a tag ref. Open gap, not yet worked around — see `CLAUDE.md`'s fuller "Tagging a release of this repository" section for the full procedure and this caveat.
- **This repository's own threat model.** `docs/security/threat-model.md` is TheForge's own STRIDE threat model, written with `template/.agents/skills/security-docs/SKILL.md` at design-tier and kept current with that skill's reconcile mode. A PR touching `bootstrap.py`, `copier.yml`'s `_tasks`/unsafe features, a root guard script, `.pre-commit-config.yaml`, `.theforge-denylist-allow`, `.theforge-denylist`, `template/.claude/`, `template/.github/workflows/`, `forge-sync`, or a control rule in `CLAUDE.md` updates it in the same PR.
- **Review gate for this repository's own PRs.** `.forge/review-gate.md` carries the full/light gate split, the mandatory self-review step, the MoSCoW triage table and the mechanical `review-gate-check` for this repository's own PRs too. Project-owned on top of that: a neutrality miss is always a Must, and before merging, strip any harness-injected attribution or identity block from the PR body and run `scripts/check-merge-text.sh <pr-number>` on the intended merge message.
- **Checking a change.** Run `scripts/check-render.sh` before every push touching `template/` or `copier.yml`: it renders the template, stages it as a project's first commit, then runs the render's own guard-script tests and pre-commit hooks against it. For a quick manual look instead, `copier copy --trust --defaults --skip-tasks --vcs-ref HEAD . /tmp/forge-render-check` and read the rendered result (`--vcs-ref HEAD`, not the default, or Copier checks out the latest tag over the working tree once one exists). In a `.jinja` file, wrap any literal `{{` or `{%` in `{% raw %}`. Refer to standing tracker issues only through the computed `*_ref` variables in `copier.yml`.
