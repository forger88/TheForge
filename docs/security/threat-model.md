# TheForge threat model

This is TheForge's own STRIDE threat model: the template repository's assets, trust boundaries, threats and controls as they are on `main`, the known gaps, and the risks accepted so far.
It covers the template repository itself, not a generated project; a generated project gets its own skeleton from `template/docs/security/threat-model.md.jinja`.
It describes the current state, never a history.
It was written with the template's own `security-docs` skill (`template/.agents/skills/security-docs/SKILL.md`), bootstrap mode, at design-tier, and is kept current with that skill's reconcile mode.

This repository has no requirements specification and no architecture description of its own.
Where the skill would cite either, this document cites the root `CLAUDE.md`, `AGENTS.md` and the ADRs under `docs/adr/` instead.
Tracking issues are cited by their title, never by number, the same convention root `CLAUDE.md` uses for its post-merge review tracker: the `no-issue-refs` hook rejects number-style references here, and numbers would not survive a publish into a fresh public repository.
A few cited titles contain their own issue's number (for example, naming the PRs a leak was found in); this document shortens those with "(...)" rather than dropping the citation, so a reader comparing a row against the tracker should expect that abridgement, not read it as a mismatch.

## 1. Scope and method

**Last reconciled against `main` @ `e3afcbe0d054a36d8a817a9680d2d24430e43d69`** (2026-11-08).

Framework: STRIDE (spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege).
Severity: **Must** (reachable today by an authenticated user or an on-path attacker), **Should** (degrades cleanly or needs a precondition), **Could** (defensive depth).

- **In scope:**
  - `copier.yml`: its questions, its `_exclude` list (which keeps every guard-script and doc-tool test file out of a render except the two rendered-state tests), its `_skip_if_exists` list and its one `_tasks` entry.
  - Everything under `template/` that a generated project receives, in two classes with different blast radii: instruction text that consuming agents obey (`template/.forge/`, `template/.agents/skills/`, `template/CLAUDE.md.jinja`, `template/AGENTS.md.jinja`, `template/docs/`), and content that executes (`template/scripts/bootstrap.py`, the other guard scripts under `template/scripts/`, `template/.pre-commit-config.yaml.jinja`, `template/.claude/settings.json` and `template/.claude/hooks/session-start.sh`, `template/.github/workflows/`, `template/.devcontainer/devcontainer.json.jinja`, the document and diagram build tooling under `template/docs/tools/`).
  - This repository's own contribution guards: `scripts/check-no-issue-refs.sh`, `scripts/check-denylist.sh`, `scripts/check-merge-text.sh`, `scripts/check-commit-identities.sh`, `scripts/check-not-raw-clone.sh`, `scripts/denylist-path.sh`, `scripts/check-denylist-not-shipped.sh`, `.theforge-denylist-allow`, `.theforge-denylist` and `.pre-commit-config.yaml`.
  - `scripts/local-full-suite.sh`, the local stand-in for the scheduled CI pass that Main Health runs on `main` (`.agents/skills/watch-main-ci/SKILL.md`, "Routine 2"), and in particular its publish mode, which writes to the hosting platform with the invoking session's credential.
  - The process rules in root `CLAUDE.md` and `AGENTS.md` that act as controls: "Agent commit identity", "TheForge stays project-neutral", "Review gate for this repository's own PRs" and "This repository's own post-merge review".
  - `scripts/publish_snapshot.py`, which publishes one released staging commit into the public repository with the invoking session's `git` credential (B2, T7).
  - `scripts/install-doc-build-tools.sh`, which downloads and installs the pinned `pandoc` and `d2` binaries and the doc-build Python packages into an agent sandbox.
  - Vendored third-party skills and their record in `template/skills-lock.json` and `template/.agents/skills/THIRD_PARTY.md`.
  - The rendered consumer files at root (ADR-0009): `.github/workflows/` (`dependency-audit.yml`, `documentation.yml`, `lint.yml`, `tests.yml`, each `workflow_dispatch`-only with `permissions: contents: read`; `review-gate-check.yml` is not rendered here), `.claude/settings.json` and `.claude/hooks/session-start.sh`, `.devcontainer/devcontainer.json`, `docs/tools/` and the root copies of `template/scripts/` (without the test files `copier.yml`'s `_exclude` keeps out of a render).
- **Not present, so not in scope:** this repository runs no workflow on a push or PR event, and builds no image.
- **Trust-boundary peers, not subjects:**
  - The hosting platform (GitHub): authentication, repository permissions, the squash-merge mechanism, tag storage, the REST API `bootstrap.py` calls.
  - Copier, which renders the template and runs its unsafe features (`_tasks`, `_migrations`, `_jinja_extensions`) only under `--trust`.
  - A consuming project's `forge-sync` skill and review gate. This repository ships that skill's text but does not run it; its correct behaviour assumes this repository's `template/` content is trustworthy, and it is the consumer's last line of review before synced text and code take effect.
  - The upstream repositories third-party skills are vendored from.
  - The agent harnesses that work on this repository and on consuming projects, including the credentials they push with.
  - PyPI, from which a consuming project's session-start hook installs pre-commit at a pinned version.

## 2. Assets

| Asset | Why it matters | Where it lives |
|---|---|---|
| Integrity of shipped instruction text | Agents in every consuming project obey it; tampering here is instruction tampering in every consumer at once | `template/.forge/`, `template/.agents/skills/`, `template/*.jinja` instruction files |
| Integrity of shipped executable content | It runs on a template user's machine at `copier copy`, in every consumer agent session (session-start hook) and on every consumer commit (pre-commit hooks) | `copier.yml` `_tasks`; `template/scripts/`; `template/.claude/`; `template/.pre-commit-config.yaml.jinja`; `template/.github/workflows/` |
| A template user's `GITHUB_TOKEN` and new repository | `bootstrap.py` runs with the token in its environment and writes labels and issues | The user's shell environment; the generated repository |
| Confidentiality of source-project material | Content is distilled from real private projects; a name, vocabulary, issue number or incident shape published here cannot be fully retracted | Anywhere in this repository's files, commit messages, commit metadata and PR text |
| The owner's identity | A personal address or name in commit metadata or PR text is disclosed once published; the owner's hosting-platform login is public by design (the repository's own path, the licence and the credits name it) and is not a denylisted term | Commit author, committer and `Co-authored-by:` fields; PR bodies |
| The denylist | A public list of what to hide is itself the leak | `.theforge-denylist`, committed to this private staging repository only, never under `template/` (`scripts/denylist-path.sh`, resolved from the script's own location so a session running from a different repository's checkout still finds it; `denylist-not-shipped` and `denylist-not-shipped-render` guard the exclusion, statically and against an actual render); `$THEFORGE_DENYLIST_FILE` or `~/.theforge-denylist` unions its own terms in alongside it when set, for that one scan (ADR-0005 amendment) |
| This repository's private history | It already carries material that must never be public | The private staging repository |
| Release points | What a consumer syncs to; with no tags, every merge to `main` | Git tags (none exist yet) and `main` |
| The `green` branch | The newest commit a full local or dispatched pass has verified, and what a release tags by default (SDLC-109, SDLC-111); a commit on it that was never fully verified becomes the next release | `refs/heads/green` on the staging repository, advanced by `scripts/local-full-suite.sh`'s publish mode |
| Integrity of the guards themselves | A weakened guard silently stops catching what it exists for | Root `scripts/` (including `check-render.sh`, `check_template_pins.py` and `local-full-suite.sh`), `.pre-commit-config.yaml`, `.theforge-denylist-allow`, `.theforge-denylist` |
| Review evidence | The only record that the review gate, post-merge review and full-suite pass ran | PR `Review:` lines; the post-merge review tracker issue; the local full-suite evidence tracker's marker comments and the `local-full-suite` commit statuses (SDLC-099) |

## 3. Actors

| Actor | How they reach the system | Privilege |
|---|---|---|
| The owner | Pushes, merges, administers both repositories; supplies the denylist's terms | Admin |
| An agent session working on TheForge | Commits, opens and merges PRs through the harness's credential; has this repository's own committed denylist by default, unioned with `$THEFORGE_DENYLIST_FILE` or `~/.theforge-denylist` when either is also set | Push to the private staging repository |
| A template user | `copier copy --trust` against the public repository, on their own machine, with a token in the environment | Full control of their own machine and token |
| A consuming project's owner and agents | `forge-sync` (`copier update`) pulls template content; agents obey the synced text and run the synced hooks | Their own repository only |
| An upstream skill author | Content vendored at a pinned ref | None directly; their text and scripts ship to every consumer once vendored |
| A public reader | Reads the public repository and its PR text | Read only |
| An outside contributor | A fork and a PR to the public repository | None until a maintainer merges |

## 5. Trust boundaries and data flows

| Boundary | Between | What crosses it | Control at the boundary |
|---|---|---|---|
| B1 Contribution | A contributor's clone and the staging repository's `main` | File changes, commit messages, commit metadata, PR text, the squash message | Pre-commit neutrality hooks; the root `CLAUDE.md` review gate (full or light); the fresh context-free reviewer; `check-merge-text.sh`; the commit-identity rule; the post-merge review |
| B2 Publish | The private staging repository and the public repository | The files of one released staging commit, minus every `.theforge-denylist*` file and with fixed rewrites applied; one templated commit message and one no-reply identity per snapshot; an annotated release tag only when asked; no staging history, branch or PR text | A post-merge review pass before each snapshot (root `CLAUDE.md`, "This repository's own post-merge review", "An extra cadence trigger"); `scripts/publish_snapshot.py`, which publishes a fresh history-free public repository, one commit per snapshot, only after a clean denylist scan (T7) |
| B3 Generation | The public repository and a template user's machine | Rendered files; the `_tasks` commands, executed with the user's environment | Copier's `--trust` gate; `copier.yml` declares one task (`bootstrap.py --from-copier`, `when` the operation is `copy`) and no other unsafe feature; `README.md` asks the user to read `bootstrap.py` first |
| B4 Bootstrap API | `bootstrap.py` on the user's machine and the hosting platform | The user's token, label and issue writes, repository listings | `check_token`; the fixed `API` host over HTTPS; `--dry-run`; idempotent `ensure_labels` and `ensure_trackers` |
| B5 Sync | A TheForge release and each consuming project, including TheForge's own root once it is a consumer of its own template | Instruction text, executable hooks and scripts, `copier.yml` (including any unsafe features) | The consumer's `forge-sync` procedure and full review gate; `_skip_if_exists` keeps project-owned files untouched; `docs/forge-overrides.md` |
| B6 Vendoring | An upstream skill repository and `template/.agents/skills/` | Skill text and, for one skill, executable scripts | Pinned `source`, `ref` and `computedHash` in `template/skills-lock.json`; credit rows in `THIRD_PARTY.md`; `check_skills_lock.py` verifies the hash on every commit, including a deletion that would otherwise match no `files:` trigger |
| B7 Raw copy | TheForge's files and a repository using them without `copier copy` | The whole tree, unrendered | `check-not-raw-clone.sh` (ADR-0004) |
| B8 Retrofit | TheForge's files and an existing, populated, independently-evolved repository, including TheForge's own root being retrofitted onto itself | The one-shot `copier copy --trust --overwrite` diff; `_tasks` writes against that repository's real issues and labels | `template/.agents/skills/retrofit-existing-project/SKILL.md`'s preconditions and tracker-reconciliation steps; `template/scripts/check_retrofit_preconditions.py`; the target's own full review gate on the sequenced landing PRs; for the self-retrofit and every later self-sync, `check_forge_sync_trust_diff.py` runs before any `--trust` run against the root, and the sync PR's "Trust diff" record is checked at the merge by `check_forge_sync_trust_record.py` (T14; I4) |
| B10 Review-gate check | Any PR against this repository (opened by anyone who can PR it, not only a collaborator) and the merging session's run of `scripts/check-merge-text.sh`, which reads that PR's own attacker-influenced body and file list | The PR body text and changed-file list, fetched through the REST API (or `gh api`) under the merging session's own credential; the lifecycle doc and `.copier-answers.yml` at the PR's base and head, when changed | Read-only API calls; any fetch failure or truncated listing aborts the scan rather than skipping a guard; the guard scripts run from the merger's own checkout, so they are the base branch's copies only if the merge is run from a base-branch checkout (a procedural assumption, not enforced; the workflow's `pull_request.base.sha` checkout pin enforced it, and a merge run from a PR branch checks the PR against its own edited guards); no workflow or write scope exists for a malicious PR body to leverage; the post-merge verify (`--verify-merged`) is read-only as well |
| B11 Local suite publish | `scripts/local-full-suite.sh` running in Main Health's sandbox and the hosting platform | Commit statuses on the run's HEAD sha; one marker-plus-table evidence comment per full run on the local full-suite evidence tracker; a fast-forward of `refs/heads/green` to that sha; all under the invoking session's own credentials | Publishing only behind `LOCAL_FULL_SUITE_PUBLISH=1`, which `watch-main-ci`'s rule reserves to Routine 2's own invocation (a rule, not enforced); the guards before each write named in T33 to T35; the fixed-path run lock in a private directory (`private_dir_ok`) |
| B12 Doc toolchain install | The upstream `pandoc` and `d2` release hosts and PyPI, and the agent sandbox running `scripts/install-doc-build-tools.sh` | Executable binaries and Python wheels, installed into `~/.local/bin` and a private venv | SHA-256 pins checked before extraction; installer versions must equal `docs/tools/document-build.json`'s toolchain versions; `==` pins in `docs/tools/requirements.txt` (T39) |

## 6. Security assumptions

- The hosting platform authenticates every push and merge and enforces repository permissions; every collaborator on the private staging repository is trusted to follow root `CLAUDE.md`.
- The staging repository stays private; material already in its history is contained only by that.
- Copier runs `_tasks`, `_migrations` and `_jinja_extensions` only under `--trust`, honours `_subdirectory` and `_skip_if_exists`, and the template user installed Copier from a trustworthy source.
- A template user's machine and Python interpreter are not already compromised.
- This private staging repository's own committed `.theforge-denylist` names the owner's standing terms (name, email addresses, other projects' names) and is never shipped under `template/`, so it never reaches a generated project; a maintainer back-porting from a real project to the *public* TheForge template instead supplies a session-local denylist naming that project's terms, kept outside every repository, since the public repository must never carry one at all. It never reaches a public snapshot either: `scripts/publish_snapshot.py` drops every `.theforge-denylist*` file before it scans and pushes (T7).
- A consuming project runs every `forge-sync` through its own full review gate and reads the diff before merging it.
- Each upstream skill repository served benign content at the ref recorded in `template/skills-lock.json` when it was vendored.
- An agent harness's credential reaches only the repositories that harness needs.
